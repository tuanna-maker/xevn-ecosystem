## Root cause (SA static audit)

`GET /api/hrm/settings-catalogs/batches/:batchId` called `getExtensionBatchDetail(batchId)` with **no** tenant/catalog partition filter. Any authenticated caller with a batch UUID could read extension rows from another tenant or operating company partition.

`POST batches/:batchId/workflow` and `POST batches/:batchId/review` had the same IDOR surface.

---

## Fix summary

| File | Change |
|------|--------|
| `settings-catalogs.controller.ts` | Batch GET/workflow/review resolve `resolveScopeContext` + `resolveHrmSettingsCatalogCompanyId`; pass `tenantId`, `catalogCompanyId`, `authorization` to service |
| `settings-catalogs.service.ts` | `assertExtensionBatchInCatalogScope` — `resolveHrmListScope(catalogCompanyId)` + tenant match + `assertResourceInHrmScope`; scoped SQL on detail fetch; mutate paths guard before UPDATE |
| `settings-catalogs.controller.spec.ts` | P0-4: group CEO `main` → `holding` partition; member `xe-du-lich/main`; D16 narrow-filter alignment |
| `settings-catalogs.service.spec.ts` | P0-4: in-scope 200, missing batch `HRM-SET-404`, cross-partition `HRM-SET-409`, tenant mismatch `HRM-SET-409` |

**Scope parity pattern:** catalog partition (`holding` for group CEO `main`) matches overview/sync/extension write paths — not full employee rollup IN list.
