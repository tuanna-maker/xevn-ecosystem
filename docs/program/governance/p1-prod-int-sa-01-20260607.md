## 1. Executive summary

Group CEO product integrity requires **two coordinated dimensions** that today are conflated in UI and partially misaligned in data:

| Dimension | XBOS surface | HRM surface | Cardinality (pilot seed) |
|-----------|--------------|-------------|--------------------------|
| **A — Legal / tenant member units** | `GET /tenant-scope/group-member-units` → `holding` + `members[]` (member **tenants** + legal entity UUID) | Not a row partition key for master workforce | **1 holding + ~4 member tenants** (evidence: `members=4`) |
| **B — Operating units (workforce partition)** | Org/business-master under `company_id=holding` (group legal anchor only) | `employees.company_id ∈ GROUP_MEMBER_SLUGS` + master `tenant_id=xevn` | **5 slugs:** `holding`, `trsport`, `logistics`, `finance`, `services` |

**User expectation** «N công ty trên XBOS = N trên HRM» is **not satisfiable** by naïve 1:1 UUID mapping. It requires an explicit **bridge contract** (§2) plus BE enrich + FE filter (§3). Until then, charts show **«Khác»** or mock labels (G-INT-01/02) and only **Employees** has a partial company filter (G-INT-05).

**SA verdict:** Accept dual-dimension model; do **not** collapse member tenants into HRM slugs without BA-data matrix. Block QC GO on integrity program while G-INT-03/04 open on touched paths.

## 2. Cardinality map — GROUP_MEMBER_SLUGS vs XBOS group-member-units

### 2.1 Architecture (two planes)

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ XBOS — Tenant / legal plane (group-member-units)                        │
│   holding (master xevn)                                                 │
│   members[]: { tenant_id, legal_entity_id UUID, name, code }            │
│   Gate: master membership only → member CEO → 403 XBOS-TENANT-403         │
└───────────────────────────────┬─────────────────────────────────────────┘
                                │ bridge (MISSING — G-INT-03)
                                ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ HRM — Operating partition plane (resolveHrmListScope rollup)            │
│   company_id slug: holding | trsport | logistics | finance | services   │
│   master rows: custom_fields.tenant_id = xevn (or default xevn)         │
│   member-tenant rows (xe-du-lich): company_id=main, tenant_id=member    │
└─────────────────────────────────────────────────────────────────────────┘
```

### 2.2 Canonical constants (code)

| Symbol | Values | Source |
|--------|--------|--------|
| `HRM_GROUP_MEMBER_COMPANY_SLUGS` | `holding`, `trsport`, `logistics`, `finance`, `services` | `hrm-list-scope.ts` L6–12 |
| `HRM_COMPANY_UUID_BY_SLUG` | Stable pilot UUIDs `10000000-…-001..005` | Same file L18–24 |
| `GROUP_MEMBER_SLUGS` (seed) | Same five | `HRM_SEED_CARDINALITY_RULES.md` §3.1, `uat-workforce.mjs` |
| XBOS `group-member-units.members[]` | Legal entities per **member tenant** | `org-foundation.service.ts` `listGroupMemberUnits()` |

### 2.3 Gap analysis vs user expectation

| Gap ID | Symptom | Root cause | Product impact |
|--------|---------|------------|----------------|
| **CARD-GAP-01** | CC settings shows **~5 legal rows** (1 holding + 4 members); HRM group rollup counts **5 operating slugs** — numbers may match by coincidence, **semantics differ** | Two dimensions (§2.1); no published mapping | User believes duplicate companies or missing unit |
| **CARD-GAP-02** | HRM chart/filter uses `GroupMemberUnitRow.id` (legal UUID) but SQL partition uses **slug** | `mapGroupMemberUnitsToHrmCompanies()` (`tenantScopeApi.ts`) produces UUID `id`s ≠ slug keys | Join fails → **«Khác»** (G-INT-02) |
| **CARD-GAP-03** | Member tenant workforce (e.g. `xe-du-lich`, `company_id=main`) **excluded** from group CEO rollup by design | `resolveHrmListScope` master partition + `assertResourceInHrmScope` tenant guard | Group CEO must **not** see tourism NV in rollup; user may expect «all legal entities' headcount» |
| **CARD-GAP-04** | No display-name SoT for five slugs in HRM FE | Slugs only have code prefixes (`HLD`, `VTH`, …) in seed lib; legal **names** live in XBOS registry / business-master | Dashboard shows slug or «Khác», not «Công ty Vận tải XeVN» |
| **CARD-GAP-05** | `coerceHrmListCompanyId()` maps `holding` → `main` (full rollup) | `hrmListScope.ts` L17–21 — correct for embed default, **breaks** «filter holding only» if dropdown value is `holding` | Filter UI cannot isolate holding partition without passing slug explicitly |

### 2.4 Target bridge contract (BA-D + Dev-BE — G-INT-03)

**Decision (SA):** Introduce **`hrm_operating_unit_registry`** view/API — read-only, XBOS-published:

| Field | Type | SoT | Example |
|-------|------|-----|---------|
| `operating_slug` | text PK | HRM seed / business-master | `trsport` |
| `display_name_vi` | text | XBOS org-foundation or business-master domain `operating_entities` | «Công ty CP Vận tải XeVN» |
| `legal_entity_id` | uuid nullable | Optional link to member legal row | null for pure operating bucket |
| `member_tenant_id` | text nullable | When unit = member tenant ops | `xe-du-lich` |
| `rollup_order` | int | UI sort | 1..5 |
| `status` | enum | active/inactive | active |

**Reconciliation script (program exit criterion):**

```text
FOR each slug IN HRM_GROUP_MEMBER_COMPANY_SLUGS:
  COUNT employees WHERE company_id=slug AND tenant partition = xevn
  MUST be > 0 (CARD-EMP-01)

FOR each active member IN group-member-units.members:
  IF mapped to operating_slug OR member_tenant_id:
    assert HRM row partition exists OR document seed gap

REPORT: |XBOS legal active| vs |HRM slugs with N>0| vs |registry rows|
```

**Non-goal:** Force `N_xbos_members === 5` — member tenants and operating slugs are **related, not equal**. Communicate in SRS: group CEO sees **operating rollup (5)** on HRM embed; CC settings shows **legal member registry (4+holding)**.

### 2.5 Display-name join (G-INT-02)

| Consumer | Join key | Display field | API |
|----------|----------|---------------|-----|
| Charts (company axis) | `company_id` slug from aggregate | `display_name_vi` | **New** `GET /api/hrm/operating-units` (proxy registry) or enrich list responses with `company_label` |
| Company filter dropdown | `operating_slug` | `display_name_vi` | Same + `fetchGroupMemberUnits` only for **legal** admin screens (`CompanyManagement.tsx`) |
| KPI/compare rail | slug | name | Do not reuse `group-member-units` UUID as HRM filter value |

## 3. Group CEO company filter — BE/FE requirements (every HRM tab)

### 3.1 BE (already partially implemented)

| Rule | Behavior | Helper |
|------|----------|--------|
| Rollup (all units) | JWT `main` + query `company_id=main` → SQL `IN (5 slugs)` + master tenant partition | `resolveHrmListScope` L137–152 |
| Single unit | JWT `main` + query `company_id=<slug>` where slug ∈ slugs → **single** slug, no rollup | ADR-GROUP-CEO §4 row «filter one unit» |
| Persist create | Group CEO body `main` → persist `holding` on TEXT tables | `resolveHrmPersistCompanyIdText` |
| UUID tables | Map slug → `HRM_COMPANY_UUID_BY_SLUG` | `pushCompanyIdUuidFilter` |
| Attendance satellites | Workforce subquery | `pushWorkforceEmployeeScopeFilter` |

**BE additions (P1-PROD-INT-BE-01):**

1. **`GET /api/hrm/operating-units`** — returns slugs + labels for master tenant group CEO (403 for member CEO).
2. **List response enrich (optional):** `company_label` on employees/contracts aggregates when `?include_labels=1`.
3. **Audit:** every embed menu API in `HRM_MENU_DATA_LINKAGE_MATRIX.md` §2.1 must call `resolveHrmListScope` — grep gate in BE evidence.
4. **Fix `coerceHrmListCompanyId` policy:** document that **`holding` as intentional single-unit filter** must bypass coercion (FE sends `company_id=holding` only when filter = holding unit; embed default stays `main`).

### 3.2 FE (P1-PROD-INT-FE-01 — G-INT-05)
